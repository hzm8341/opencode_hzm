## 1. 项目现状分析

### 1.1 项目技术栈

- **运行时**: Bun 1.3.5+
- **语言**: TypeScript
- **构建工具**: Bun.build() with compile option
- **包管理**: Bun workspaces (monorepo)

### 1.2 现有构建系统

项目已具备完整的构建系统，位于 `packages/opencode/script/build.ts`：

**关键特性**:
- ✅ 支持多平台构建（Linux x64/arm64, macOS x64/arm64, Windows x64）
- ✅ 使用 `Bun.build()` 的 `compile` 选项生成可执行文件
- ✅ 支持 musl/glibc 两种 Linux ABI
- ✅ 支持 AVX2 baseline 版本（兼容旧 CPU）
- ✅ 自动处理平台特定的原生依赖（@parcel/watcher, @opentui/core）

**构建命令**:
```bash
# 构建当前平台
bun run packages/opencode/script/build.ts --single

# 构建所有平台
bun run packages/opencode/script/build.ts
```

**输出位置**: `packages/opencode/dist/opencode-<platform>-<arch>/bin/opencode`

### 1.3 当前构建流程

```typescript
Bun.build({
  compile: {
    target: "bun-<platform>-<arch>",  // 例如: "bun-linux-arm64"
    outfile: "dist/opencode-<platform>-<arch>/bin/opencode",
    execArgv: [`--user-agent=opencode/${version}`, "--"],
  },
  entrypoints: ["./src/index.ts", parserWorker, workerPath],
})
```

## 2. 可行性评估

### 2.1 Bun 编译特性分析

**Bun.compile() 的工作原理**:
- Bun 的 `compile` 选项会创建一个**自包含的可执行文件**
- 可执行文件内嵌了 Bun 运行时和所有 JavaScript 代码
- **理论上不需要在目标系统安装 Bun**

**验证要点**:
1. ✅ 可执行文件是否包含所有依赖
2. ⚠️ 原生模块（native addons）的处理
3. ⚠️ 动态加载的资源文件（如 worker 文件）
4. ⚠️ 外部系统依赖（如系统库）

### 2.2 依赖分析

#### 2.2.1 JavaScript 依赖
- ✅ **已处理**: Bun.compile 会自动打包所有 JS/TS 代码
- ✅ **已处理**: 使用 `conditions: ["browser"]` 处理条件导入

#### 2.2.2 原生依赖（Native Addons）
项目使用以下原生模块：

1. **@parcel/watcher** - 文件系统监控
   - 提供平台特定二进制文件（已通过 `bun install --os="*" --cpu="*"` 安装）
   - ⚠️ **需要验证**: 这些二进制文件是否被正确打包到可执行文件中

2. **@opentui/core** - UI 框架
   - 包含 parser.worker.js（已通过构建脚本处理）
   - ✅ **已处理**: 通过 `bunfsRoot` 路径引用

3. **tree-sitter-bash** - 代码解析
   - 使用 WebAssembly
   - ⚠️ **需要验证**: WASM 文件是否正确打包

#### 2.2.3 系统依赖
- **Linux**: 可能需要 glibc 或 musl（已支持两种 ABI）
- **macOS**: 需要 macOS 10.15+（通过 target 指定）
- **网络**: 需要网络访问（用于 API 调用，非打包问题）

### 2.3 平台兼容性

#### 2.3.1 Linux 支持
- ✅ **x64 (glibc)**: 完全支持
- ✅ **x64 (musl)**: 完全支持（Alpine Linux 兼容）
- ✅ **arm64 (glibc)**: 完全支持
- ✅ **arm64 (musl)**: 完全支持

#### 2.3.2 macOS 支持
- ✅ **arm64 (Apple Silicon)**: 完全支持
- ✅ **x64 (Intel)**: 完全支持（但可能在未来被弃用）

## 3. 潜在问题与风险

### 3.1 高风险项

1. **原生模块打包**
   - **问题**: @parcel/watcher 等原生模块的二进制文件可能未正确打包
   - **影响**: 运行时可能找不到原生模块
   - **解决方案**: 验证并可能需要手动复制二进制文件

2. **Worker 文件路径**
   - **问题**: 代码中使用 `/$bunfs/root/` 路径引用 worker 文件
   - **影响**: 在独立可执行文件中可能无法找到 worker
   - **解决方案**: 需要验证或修改为相对路径

3. **动态资源加载**
   - **问题**: 某些资源可能在运行时动态加载
   - **影响**: 资源文件可能缺失
   - **解决方案**: 确保所有资源都被正确打包

### 3.2 中风险项

1. **文件大小**
   - **问题**: 包含 Bun 运行时的可执行文件可能较大（预计 50-100MB）
   - **影响**: 下载和分发时间
   - **解决方案**: 可接受，现代应用常见大小

2. **启动性能**
   - **问题**: 自包含可执行文件启动可能稍慢
   - **影响**: 用户体验
   - **解决方案**: 通常可接受（< 1秒）

### 3.3 低风险项

1. **符号链接处理**
   - **问题**: 某些系统可能不支持符号链接
   - **影响**: 最小，主要影响安装脚本
   - **解决方案**: 已有 Windows 特殊处理

### 4.2 阶段二：问题修复与优化（2-3天）

#### 4.2.1 原生模块处理

**问题**: 原生模块二进制文件可能未正确打包

**解决方案**:
1. 检查 `@parcel/watcher` 等原生模块的安装位置
2. 在构建脚本中添加复制原生模块的逻辑
3. 修改代码以使用相对路径引用原生模块

**实施步骤**:
```typescript
// 在 build.ts 中添加
const nativeModules = [
  '@parcel/watcher',
  // 其他原生模块
]

for (const module of nativeModules) {
  // 复制原生模块到输出目录
  await $`cp -r node_modules/${module} dist/${name}/node_modules/`
}
```

#### 4.2.2 Worker 文件路径修复

**问题**: Worker 文件使用绝对路径

**解决方案**:
1. 修改构建脚本，将 worker 文件复制到可执行文件目录
2. 修改代码，使用相对路径或环境变量
3. 使用 `__dirname` 或 `import.meta.url` 获取可执行文件位置

**实施步骤**:
```typescript
// 在 build.ts 中
await $`cp ${parserWorker} dist/${name}/bin/parser.worker.js`

// 在代码中使用
const workerPath = path.join(__dirname, 'parser.worker.js')
```

#### 4.2.3 资源文件打包

**问题**: 动态加载的资源文件可能缺失

**解决方案**:
1. 识别所有动态加载的资源
2. 在构建脚本中复制到输出目录
3. 修改代码使用相对路径

## 5. 技术方案对比

### 5.1 方案一：使用 Bun.compile（当前方案）✅ 推荐

**优点**:
- ✅ 已集成到项目中
- ✅ 支持多平台
- ✅ 自包含运行时
- ✅ 构建速度快

**缺点**:
- ⚠️ 需要处理原生模块
- ⚠️ 文件大小较大

**适用场景**: 当前项目的最佳选择

### 5.2 方案二：使用 pkg（Node.js 打包工具）

**优点**:
- ✅ 成熟的打包工具
- ✅ 支持多平台

**缺点**:
- ❌ 需要 Node.js 运行时
- ❌ 不支持 Bun 特定特性
- ❌ 需要大量代码修改

**适用场景**: 不推荐，项目使用 Bun 而非 Node.js

### 5.3 方案三：使用 esbuild + 自定义打包

**优点**:
- ✅ 灵活的打包配置

**缺点**:
- ❌ 需要手动处理运行时
- ❌ 开发工作量大
- ❌ 维护成本高

**适用场景**: 不推荐，过于复杂

### 5.4 方案四：使用 Docker 容器

**优点**:
- ✅ 完全隔离的环境
- ✅ 易于分发

**缺点**:
- ❌ 需要 Docker 运行时
- ❌ 不是真正的可执行文件
- ❌ 启动开销大

**适用场景**: 不推荐，不符合需求
